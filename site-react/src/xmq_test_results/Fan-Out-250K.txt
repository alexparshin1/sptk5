Scenario: Fan-Out 250K - Fan-Out-5-1000-5-250K-5min.json
          5 publishers / 5 topics / 1000 subscribers, each subscribed to all 5 topics.
          50 msg/s per publisher = 250/s in, delivered as 250/s x 1000 = 250k/s out.
          QoS 1, 16B payload, MQTT 3, 5 minutes.
          Mirrors the Open MQTT Benchmark Suite's singlenode-fanout-5-1000-5-250K case,
          duration-bound rather than message_count-bound (the parent scenario stops after
          1000 published messages, which at this rate lasts seconds).
Date:     2026-07-30
Server:   AWS c5n.4xlarge, 16 vCPU (8 physical cores x 2 threads), 40Gb RAM
Client:   AWS c5n.4xlarge, 16 vCPU, 40Gb RAM, same AZ + cluster placement group
Client:   xmq_scn 0.9.13

Only 1005 connections, and the inbound side is trivial at 250 msg/s. What this measures
is delivery fan-out: one received message becoming a thousand sends.

CPU percentages are of ONE core: 1600% = all 16 vCPU. xmq_server pins one thread per
physical core (its shipping default, faster than --no-cpu-affinity), so its ceiling is
800%; EMQX and Mosquitto run unpinned with all 1600% available.

NOTES
  The client was never the bottleneck: xmq_scn peaked at 442% of 1600% available
  (~28% of the client box) during the heaviest run. Both 250k/s results are broker
  measurements, not load-generator artifacts.

  Each broker was restarted immediately before its own run. Runs were strictly
  sequential - two brokers competing for the same cores would corrupt both results.
