  2880us against 0.9.13's 2480us. This was first written up here as a 16% regression;
  it is not one, and the retraction is the same evening's work.

  Repeating this run three more times - identical binary, identical configuration,
  broker restarted before each - gave 3380, 3081 and 2658us. The scenario's spread
  between runs is 27%, more than twice the difference it was supposed to prove, and
  2480us sits within 7% of the best of the four. One run against one run says nothing
  here, which is what this file's own discipline says elsewhere and what this row
  ignored.

  Why this scenario moves so much, when Fan-In and Point-To-Point reproduce to a few
  microseconds across six weeks, is not established. An explanation offered here
  first - that delivery is sharded by the publisher's id, so five publishers could
  not fill eight shards - is wrong and has been withdrawn: the sender's hash only
  picks the thread that starts a fan-out, and that thread spreads the subscribers
  across every shard. What is true is that with five publishers only five of the
  eight threads ever start one, but that is 250 messages a second against 250000
  deliveries, and not where the time goes.

  The CPU column above is not comparable with 0.9.13's either, and for a duller reason
  than the code: this run's sampler was started 3.5 minutes into five, so its 612%
  is a mean over steady state alone, while 0.9.13's 329% is a mean over the whole run
  including the connect phase and the ramp, when the broker is nearly idle. The peaks,
  which do not depend on the window, are 615% and 595% - the same figure. Fan-In,
  sampled here for its whole run, shows the same shape: 239% mean against a 398% peak.

  So nothing in this row survives as a difference between the versions. The bench
  agrees: interleaved, the two builds cost 253% and 257%, and the phase breakdown puts
  the send path at 3592us against 3583us measured before batching existed.
  
  CPU caveat: the sampler was started 3.5 minutes into this 5-minute run, so its mean
  covers the last 80 seconds only. The latency figure is the whole run.
