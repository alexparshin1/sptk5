    - emqx.conf is tuned per EMQX's own performance guide (process_limit 4194304,
      max_ports 2097152, acceptors 64, backlog 8192, max_connections 2000000)
    - the client had ample headroom (275% of 1600%)

  (xmq_scn vs XMeter). Treat this as a result for this version under this harness,
  not as a general statement about EMQX.

  Worth noting alongside: Mosquitto held the full rate on ONE core in this same
  scenario, while EMQX saturated thirteen. That gap is large enough to suggest
  something pathological in 5.8.9's shared-subscription dispatch rather than a
  simple capacity limit, and is worth investigating before drawing conclusions.

  latency IMPROVES over the run (946ms peak down to 145ms) rather than diverging.
  It beat EMQX here on both throughput and latency, using one core against thirteen.

  The cost is memory: 31.4 Gb peak on a 40Gb host, leaving 4.6Gb free. This config
  sets max_inflight_messages and max_queued_messages to 0 (unbounded), so the early
  backlog - visible as the 236-946ms latencies in the first half - is absorbed as
  heap rather than as drops, and glibc does not return it afterwards. A finite queue
  cap would trade that memory for message loss.

  Also beats its own published figure for this scenario (41000/s at 12476ms).

NOTES
  TcpExtListenOverflows: 2527 across the whole suite. Mosquitto 2.0.22 hardcodes
  listen(sock, 100) and cannot absorb 50500 clients arriving at the connect rate;
  net.core.somaxconn (65535 here) does not help, since the kernel applies
  min(backlog, somaxconn). A connect-phase artifact, unrelated to steady-state
  throughput. EMQX uses backlog 8192 and XMQ 4096 x 4 SO_REUSEPORT listeners.

  Each broker was restarted immediately before its own run, so no run inherited
  memory a previous one retained. Runs were strictly sequential.
