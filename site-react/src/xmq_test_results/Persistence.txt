  READ THIS BEFORE COMPARING IT WITH THE XMQ FIGURE ABOVE. The two are not measuring
  the same mechanism, and this run had no persistence of any kind.

  XMQ writes session and message state to Redis - a separate server, over the network,
  paying a round trip - and the XMQ numbers are what that costs.

  FlashMQ was run with NO storage_dir configured, which is how it was already set up on
  this host (the directive was present but commented out) and how it was left. Without
  storage_dir FlashMQ writes nothing to disk at all: sessions, retained messages and
  wills live in memory and are gone when the process is. MQTT session semantics were
  exercised - clean_session was off and subscribers kept their sessions - but nothing
  here survives a restart, let alone a crash.

  So this figure is FlashMQ's in-memory session handling with durability switched off
  entirely. It is not comparable to the XMQ figure above, and it is not even FlashMQ's
  own persistent configuration.

  WHAT WOULD MAKE IT COMPARABLE: re-run FlashMQ with storage_dir set, which is the
  measurement that was intended here and has not been taken. Even then FlashMQ's disk
  writes and XMQ's Redis round trip are different guarantees. The other half of a fair
  comparison is XMQ measured with persistence off - see the persistence-cost figures,
  ~49.8K/s off versus ~25.2K/s on for 100K sessions.
